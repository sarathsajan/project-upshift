Project Upshift - Code Review Report
====================================
Date: 2026-08-09
Scope: Repository review across API integration scripts, credential loaders, and the alert-bot orchestration flow.

## Executive Summary
Project Upshift is a research-oriented Python workspace that demonstrates Upstox SDK API examples for user profile, margin, holdings, brokerage, instruments, LTP quotes, and order placement. The code is modular by domain but is still a collection of standalone scripts rather than a cohesive application or service.

The overall implementation has a small, readable footprint, but it also carries material risks that should be addressed before treating this as anything beyond an exploration workspace:
- Secrets are loaded from a local JSON file and repeated in many folders.
- Critical live trading behavior, such as placing an order, is hard-coded and executed directly in a script.
- There is no automated test suite, no clean service boundary, and no standard validation around API responses.
- Error handling is present for SDK exceptions but not for missing credentials, invalid JSON, bad data shapes, network issues, or response contract drift.

## Critical Issues

### 1) Secrets are stored and loaded as workspace-local JSON at runtime
Relevant files:
- user/read_creds.py:1-10
- market/read_creds.py:1-10
- portfolio/read_creds.py:1-10
- orders/read_creds.py:1-10
- charges/read_creds.py:1-10
- alert-bot/read_creds.py:1-10
- env.json (repository root)

Problem:
Each module reads from the same runtime credential file by resolving a relative path from the current working directory. That is a weak production security posture because secrets are copied into a repository-local file and then loaded by scripts. The `logout.py` sample also injects a literal placeholder token string into the configuration (`{your_access_token}`), which indicates a missing secure credential flow.

Why it matters:
- Token leakage risk through source control, logs, screenshots, or file sharing.
- No environment distinction between dev, sandbox, and production credentials.
- The workspace contains credential-loading logic copied multiple times, increasing drift and maintenance cost.

Suggested solution:
Move credential resolution to environment variables and a shared access layer, e.g. `os.getenv(...)` or a secure secrets manager. Keep the credential file outside the repo root or ignore it via git and load it only through an approved configuration loader.

Example:
```python
import os
import upstox_client

configuration = upstox_client.Configuration()
configuration.access_token = os.environ.get("UPSTOX_ACCESS_TOKEN")
if not configuration.access_token:
    raise RuntimeError("UPSTOX_ACCESS_TOKEN is not configured")
```

Rationale:
This aligns the code with the principle that sensitive runtime values should not be checked into the repository and should be resolved in a single, auditable place.

### 2) Live trading is performed directly from a script with fixed order parameters
Relevant files:
- orders/place_order.py:1-28
- alert-bot/manage.py:1-86

Problem:
`place_order.py` creates a `PlaceOrderV3Request` instance with an explicit instrument token, quantity, product, validity, price, transaction type, and flags, then executes it immediately. The alert-bot workflow reads user holdings and then emits BUY/SELL/HOLD decisions but does not apply any strategy guard rails or transaction control.

Why it matters:
- This is a direct market-facing side effect that should be protected by business validation, risk limits, dry-run paths, and an execution interface.
- There is no preflight validation or confirmation workflow before sending a live order.
- The alert-bot can effectively make operationally meaningful decisions from runtime status; no production-grade policy layer exists.

Suggested solution:
Separate API calls from orchestration and build a small service/controller layer that validates order intent before it reaches the broker API. Introduce a strategy contract with preconditions and a dry-run mode.

Example:
```python
def submit_order(request: PlaceOrderV3Request, dry_run: bool = True):
    if not dry_run:
        return api_instance.place_order(request)
    return {"mode": "dry-run", "request": request}
```

Rationale:
This creates an explicit execution boundary and reduces the chance that standalone examples become accidental production workflows.

### 3) The codebase has no test safety net or runtime verification contract
Relevant files:
- Any API example under the project directories.
- README.md:1-129

Problem:
The repository has API examples, but no tests, mocks, fixtures, or integration smoke checks. The examples are meant to be run manually and rely on a live Upstox token. There is no guard against API-shape drift or response parsing failures beyond `ApiException` handling.

Why it matters:
- Failures from contract changes or incorrect credentials will surface only at runtime.
- Debugging is difficult because examples print raw API response objects rather than mapping them to domain-safe structures.
- A direct production path exists through order execution and holdings-based bot logic with no quality gate.

Suggested solution:
Introduce lightweight tests around response parsing and shared config initialization. Add an integration-safety utility that checks required environment variables before API calls.

Example:
```python
import pytest

def test_token_loaded_from_env(monkeypatch):
    monkeypatch.setenv("UPSTOX_ACCESS_TOKEN", "abc")
    token = os.environ.get("UPSTOX_ACCESS_TOKEN")
    assert token == "abc"
```

Rationale:
Test coverage improves confidence that the project stays aligned with the broker SDK contract and prevents accidental runtime breakage.

## Suggestions

### 4) Shared credential loading is duplicated and should be centralized
Relevant files:
- user/read_creds.py:1-9
- market/read_creds.py:1-9
- portfolio/read_creds.py:1-9
- orders/read_creds.py:1-9
- charges/read_creds.py:1-9
- alert-bot/read_creds.py:1-9

Problem:
Every folder carries a copy of the credential-loading pattern. The code reads a file, loads `UPSTOX_ACCESS_TOKEN`, and sometimes also `UPSTOX_ACCESS_TOKEN_SANDBOX`. This is clean for a prototype but brittle for a longer-lived codebase.

Suggested solution:
Create a single shared module, for example `common/config.py`, that exposes a `get_upstox_config()` function and performs token validation. The individual scripts should import from that module instead of each own credential script.

Rationale:
This reduces maintenance cost and keeps credential path logic consistent.

### 5) Runtime state is tightly coupled to printing and logging instead of structured logging
Relevant files:
- alert-bot/manage.py:1-86
- user/get_profile.py:1-19
- user/get_fund_and_margin.py:1-18
- portfolio/get_holdings.py:1-22

Problem:
The logs are assembled as simple strings in a list, printed to stdout, and then written to a file in a fixed path. The code is fine for an internal research log but not for diagnostics or a production event trail.

Suggested solution:
Use the Python `logging` module with a configurable format and handler. Add a `--dry-run` CLI entry point or a `json` output mode for machine consumption.

Example:
```python
import logging
logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
```

Rationale:
Structured logging gives operational visibility while keeping the console and file outputs deterministic.

### 6) API response handling is shallow and should validate business invariants
Relevant files:
- portfolio/get_holdings.py:14-22
- orders/place_order.py:17-28
- market/get_ltp_quotes.py:22-27
- user/get_profile.py:13-19

Problem:
The code calls API methods and prints the raw response. There is no validation that the response contains the fields or object types the script expects before the code accesses them.

Suggested solution:
Introduce a response-normalization layer that checks `api_response` and `api_response.data` presence before reading nested fields.

Example:
```python
if not getattr(api_response, "data", None):
    raise ValueError("Broker API returned an empty holdings payload")
```

Rationale:
This prevents `AttributeError` and contract-break issues from becoming difficult-to-diagnose runtime failures.

### 7) The repository layout is domain-driven but not layered enough for safety
Relevant files:
- README.md:1-129
- alert-bot/manage.py:1-86

Problem:
The repository separates APIs by business domain, which is good, but no data domain model or shared client layer exists. The scripts import the SDK classes and credentials directly and each script is a one-shot entry point.

Suggested solution:
Introduce a small package structure like `core`, `services`, and `strategies`, then route all broker-calls through common wrappers.

Rationale:
The layering gives you a stable place for validation, rate limiting, retries, and result normalization.

## Specific Findings by File

### orders/place_order.py
- Lines 5-6: `Configuration()` and `configuration.access_token = read_creds.UPSTOX_ACCESS_TOKEN` create a one-shot runtime connection.
- Lines 7-19: Hard-coded order request parameters are instantiated without any external configuration file or CLI parser.
- Lines 20-28: API call is immediately executed within a `try/except` and outputs the raw response to stdout.

### alert-bot/manage.py
- Lines 8-12: `generate_log()` writes a string to stdout and appends it to a collector list.
- Lines 15-17: Holdings and profile retrieval happen in sequence without response shape checks.
- Lines 24-52: The logic decides SELL if `last_price` meets profit threshold, BUY if at-or-below average price, or HOLD otherwise. This is potential live decision logic but is not guarded.
- Lines 54-57: The final log is written to a timestamp-based file path, but there is no safe rotation or retention strategy.

### instruments/get_instrument_info.py
- Lines 10-22: The instrument metadata download uses a remote URL and writes files to the current working directory.
- Lines 23-49: The script performs a regex search over the loaded instrument payload and prints the results. The data is fetched from the web each time it is run; no caching or version pin exists.

### user/logout.py
- Line 7: Placeholder access token is hard-coded as the literal string `'{your_access_token}'`.
- Lines 10-16: A logout API call is made with an unsafe live token configuration outside the credential loader pattern.

## Conclusion
This repository should be treated as an exploratory SDK integration sandbox rather than a production-ready trading system. The code is readable and well-organized by domain, but the security posture, runtime control boundary, and lack of automated safeguards require a design-level hardening pass before it can be considered for any execution beyond testing.

Recommended next steps:
1. Replace credential loading with environment-managed secret resolution.
2. Introduce a service boundary for order operations and a dry-run mode.
3. Add tests around the API integration helpers and response parsing.
4. Introduce structured logging and observability for trade flows.
5. Document which scripts are safe examples and which are executable production paths.
